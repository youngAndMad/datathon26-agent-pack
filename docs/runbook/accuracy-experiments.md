# Локальные эксперименты качества

Инструмент `scripts/accuracy_experiments.py` готовит отдельные профили, проверяет
объявленное разделение данных и сравнивает агрегированные метрики. Он не запускает
модель, не читает видео, не скачивает зависимости и не меняет `configs/`, версии
Python или статус правил. Результаты подготовки находятся в игнорируемом Git
каталоге `data/accuracy-experiments/`.

## 1. Подготовка

Из корня репозитория в PowerShell (замените Python на окружение нужного backend):

```powershell
.venv-windows\Scripts\python.exe scripts\accuracy_experiments.py prepare --output data/accuracy-experiments/run-01 --baseline-rules CW11,CW12 --candidate-rules CW01,CW02,CW04
```

Каталог должен быть новым: существующие эксперименты не перезаписываются.
`baseline.json` — точная копия текущего профиля. `short-dense.json` меняет только
стратегию первичной выборки: более короткие окна с удвоенной частотой и меньшим
перекрытием. Число кадров полного окна укладывается в существующий лимит.
`resolution.json` увеличивает только длинную сторону первичного кадра в 1,5 раза.
Последние два профиля экспериментальные и не измерены на конкретном устройстве.

У плотного профиля сохранены редкие резервные уровни для длинных записей.
Фиксируйте реально выбранный уровень из отчёта: если сработал fallback, нельзя
приписывать результат плотной выборке. Унаследованные оценки стоимости окна
не являются замером Windows/CUDA. Не меняйте пяти минутный предел ради эксперимента.

`plan.json` содержит отдельные добавления кандидатных правил к базовому набору.
Это план локальной оценки, а не одобрение правил для production. При испытании
правил используйте baseline-профиль; при испытании кадров сохраняйте базовый набор
правил. Не смешивайте изменения в одном сравнении.

## 2. Разделение данных

Создайте локальный JSON-манифест с метаданными, без описаний сцен. Пример ниже
синтетический; хеши должны быть вычислены локально по вашим файлам:

```json
{"clips": [
  {"clip_id": "synthetic-a", "scene_group": "scene-a", "sha256": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa", "split": "dev", "previously_used": true},
  {"clip_id": "synthetic-b", "scene_group": "scene-b", "sha256": "bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb", "split": "holdout", "previously_used": false}
]}
```

```powershell
.venv-windows\Scripts\python.exe scripts\accuracy_experiments.py validate-split data/accuracy-experiments/local-manifest.json
```

Допустимые части: `train`, `dev`, `holdout`. Валидатор отклоняет повторные ID,
одинаковые SHA-256 или группы исходных сцен в разных частях, а также отсутствие
явного `previously_used`. Разные ракурсы, монтаж и дубли одной постановки должны
получить одну группу; SHA-256 сам этого не определит. Инструмент не открывает
файлы для подтверждения хешей и не удостоверяет независимость набора.

Результат отличает объявленные новые holdout-записи от уже использованных.
Нельзя сделать прежние 41 ролик независимыми простым переименованием split.
Нужны новые записи, включая другой ракурс, без подбора параметров по их ответам.
Этот манифест не заменяет файл `dev_eval.py --splits`: последний пока принимает
отдельное отображение `clip_id -> split`. Поддерживайте их соответствие локально.

## 3. Измерение человеком на локальном устройстве

Сначала сохраните baseline, затем по одному запускайте выбранные варианты через
существующий `scripts/dev_eval.py --profile <профиль> --rules <набор> --split dev
--splits <локальное отображение split> --run <новое имя>` в окружении реальной
локальной модели. Backend, веса, квантизация, устройство, данные и правила должны
совпадать, если они не являются исследуемым фактором. Запуски выполняйте
последовательно, через имеющуюся GPU reservation; не запускайте одновременно с
обслуживанием пользовательских заданий. Организаторские файлы и результаты
отдельных роликов не передавайте облачным агентам.

Сохраняйте время загрузки модели отдельно от времени задания, пиковые RAM/VRAM,
время по этапам и выбранные уровни. Проверяйте и короткие, и максимальные по длине
ролики, таймауты и OOM; готовность `/readyz` не доказывает успешный анализ.
Сравнивайте качество завершённых проверок вместе с долей завершения и точностью
среди всех отправленных роликов. Пропуски из-за технического отказа нельзя скрыть
отчётом только по успешным заданиям. Для таймкодов и типов нужна проверенная
локальная разметка; число выданных событий по правилу не является его accuracy.

## 4. Сравнение агрегатов

```powershell
.venv-windows\Scripts\python.exe scripts\accuracy_experiments.py compare data/dev_eval/baseline/summary.json data/dev_eval/dense/summary.json
```

Вывод содержит разрешённые числовые агрегаты, включая `completed_classification`,
`accuracy_all_submissions`, отказы и задержки. Не копируются сцены, пути, отдельные
ролики или произвольные строковые поля. Индекс входа соответствует порядку файлов.
Проверки `match/different/missing` сравнивают объявленные хеши выбора данных,
реестра и модели, backend и устройство. Разные/отсутствующие значения требуют
разбора человеком; совпадение метаданных не доказывает корректность эксперимента.
Старые top-level TP/FP/TN/FN могут включать штрафы за технические ошибки — для
качества распознавания используйте новую секцию `completed_classification`.
Инструмент намеренно не выбирает «победителя» автоматически.

## 5. Что остаётся решением локального проверяющего

- Подтвердить нормативный источник РК, условия и контрпримеры каждого правила;
  включать production-правило только после проверенной оценки, не ради recall.
- Разобрать пропуски по этапам: правило отсутствует, действие вне кадров,
  первичное распознавание, отклонение кандидата, техническая ошибка.
- После выбора параметров провести отдельную проверку на новых сценах и ракурсе.
- Решать вопрос LoRA/дообучения после выявления устойчивых ошибок распознавания.
  Нужны локальная разметка, отрицательные и неразборчивые случаи, групповой split
  и сравнение после квантизации. Тестовые ролики жюри для обучения запрещены.

Ни один подготовленный профиль не обещает рост с 56%. Синтетические тесты этого
инструмента подтверждают подготовку и контроль метаданных, а не качество модели.

## Проверка кода без конкурсных данных

```powershell
.venv-windows\Scripts\python.exe scripts\qa_accuracy_tests.py
.venv-windows\Scripts\python.exe -m unittest tests.inference.test_accuracy_contract tests.test_dev_eval_metrics tests.test_accuracy_experiments tests.pipeline.test_accuracy_diagnostics tests.rules.test_omission_routing
```

Первый скрипт запускает существующие тесты парсера, адаптера, правил и пайплайна
с временными папками внутри рабочего каталога. Они наследуют обычные права
каталога Windows. Тест символической ссылки пропускается только при отсутствии
системного права на её создание; остальные проверки путей продолжают работать.
