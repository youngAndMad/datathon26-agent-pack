## Features
1. **Observability panel «Охват проверки»** (done screen):
   - «Проверенные правила» lists each rule with an icon and a text status: ✓ проверено / ◐ проверено частично / ✕ нельзя проверить по видео. The border styling also differs, so status is not shown by colour alone.
   - Each rule shows its `note_ru`.
   - Unverifiable intervals are clickable time ranges that seek to their start. They also appear as hatched segments on the timeline, with a legend; the segments are clickable too.
   - «Качество записи» lists `quality_notes_ru`.
   - When `review_required` is set, a neutral info badge reads «Требуется просмотр человеком — это свойство проверки, а не вывод о нарушении».
   - For no_violation results the verdict card still shows the qualification. The panel adds a warning that lists the rules that were not fully checkable, or says that every rule was checked. If coverage data is missing, it says so.
   - The video section now also appears when only unverifiable intervals exist.
2. **Event clip «Показать фрагмент»:**
   - Seeks to `max(0, start−3)` and plays. A `timeupdate` handler stops at `end+3`, clamped to the duration. With «Повторять фрагмент события» checked, it jumps back to the clip start instead.
   - Any other seek cancels the clip.
   - When the media cannot play, the button is disabled with an evidence-only hint.
   - Clicking evidence or a time still seeks to t−1. Seek notes are now visible (aria-live).
3. **Reviewer decision («Решение проверяющего») on each event card:**
   - Buttons: Подтверждено / Отклонено / Требует проверки.
   - Optional fields: comment, corrected type, and corrected time with a «= текущее время видео» helper.
   - Sends `POST …/events/{id}/review` with exactly `{decision, comment, reviewer, corrected_type|null, corrected_timecode_sec|null}`.
   - Shows the latest decision with the reviewer and local time, plus a count when there are several. Errors appear inline.
   - It sits in a separate box and never changes the verdict, the event text or the event type. The verdict card notes that reviews are stored separately.
   - Reviewer name lives in memory and in `sessionStorage["cashwatch.reviewer"]`. The key is never stored.
   - «Сообщить о пропущенном событии» (top of results, in «Проверка сотрудником») opens a form pre-filled with the current video time, or asks for manual entry if the video is unavailable. It posts to `events/missed/review` with decision `missed`. Reports are listed under «Сообщения о пропущенных событиях».
4. **Export «Скачать отчёт (JSON)»:**
   - Authorized fetch of `/export`, then a blob download.
   - The filename comes from Content-Disposition (`filename*` UTF-8 is preferred, and the name is sanitized). The fallback is `cashwatch-<id>.json`.
   - The object URL is revoked after 1 s. Errors appear inline.
5. **History:**
   - `GET /api/v1/jobs?limit=50[&status=]`, newest first, as the server returns it.
   - Columns: time, id, status, result or error text, event count, «N из M» reviewed, review-required badge, and a «ТЕСТ» badge for mode=test.
   - Status filter, a «Обновить» button, and «Открыть»/«Следить» buttons.
   - A 401 returns to key entry.
6. **Fixture mode** (`npm run dev:fixtures`):
   - The listed jobs (0001 violation, 0002 failed) open instantly.
   - The list is filtered by status, and `reviewed_event_count` updates after reviews.
   - POST review echoes an EventReview with status 201. It returns 404 for an unknown event and 409 when the job is not done.
   - GET reviews works.
   - Export returns `{job_id, exported_at, report(with reviews), versions:null, coverage:null, original_jury_result}` with Content-Disposition.

## Limitations / assumptions
- **Real API not exercised:**
  - I assume the review POST returns 201 with an EventReview JSON body.
  - I assume `/jobs` returns `{jobs: [...]}`.
  - I assume `/export` sets Content-Disposition. If it does not, the fallback name is used.
- **Reviews are loaded only from `report.reviews` when the result opens.** `getReviews` exists but is not polled. Reviews made in another tab appear after reopening.
- **A missed report counts as "missed"** if `event_id == "missed"` or `decision == "missed"`.
- **Opening a done job from history goes through the normal polling path.** It shows "Идёт анализ" for one poll cycle (about 1.5 s or less) before the result. It also runs the same jury/report consistency check.
- **History times use the browser locale, in local time.** I did not add pagination beyond `limit=50`.
- **No detection quality is shown or implied by any of these tests.**
